# RAG 工程：成本与延迟预算

> 把单次问答拆成可相加的成本项，先定住 p95 与单价上限再反推候选数与模型档位。

## 单次问答的成本分解
一次问答的开销可拆成四项相加：查询编码调用、ANN 检索摊到单请求的内存与 CPU、重排算力（按实际打分的 query-doc 对数计）、生成端的 prompt 与 completion token。生成端通常吃掉七成以上，prompt token 随证据条数近似线性增长——每多一段 512 token 的片段就多一份输入费，completion 长度却与证据条数基本无关。

## 离线成本必须摊销
全库向量化、周期性重建、倒排建索引按周期发生，直接拿来与单次问答比没有意义。把周期内的离线总花费除以同期问答量，折成每次问答的分摊值再相加。百万片段的库重编码一轮，摊到月均十万次问答上不足一毫；若月问答量只有几千次，这一项会反超生成成本，该调的是重建频率而不是上下文长度。

## 先定预算再反推参数
顺序应当是业务先定死两条硬线，例如 p95 不超过 3 秒、单次不超过 2 分钱，再从预算倒推参数：留给生成的 token 额度决定最终保留几条证据，留给检索的毫秒额度决定候选规模与是否启用 cross-encoder。单价撑不住旗舰模型时，就把改写和重排降档，只在生成端保留大模型。

## 超预算时的降级顺序
按对正确率的影响从小到大砍：先停掉多子查询扩展，再压缩证据条数，然后把重排换小模型或缩小打分范围，最后才动生成模型档位。每砍一项都要在回归集上复核[评估指标](note://rag-evaluation-metrics)，正确率跌超 2 个百分点就换下一条路。
