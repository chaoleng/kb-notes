# omp Harness：交付前的验证契约

> 交付前必须跑真实路径而非只跑测试文件，bug 要先复现后确认，子 Agent 的完成声明需要主 Agent 复验。

## 跑真东西，不是跑测试文件

验证的对象是改动后的可观察行为：命令行改动就启动程序敲一遍，接口改动就打一次请求看返回，界面改动就打开页面确认渲染。只跑一个断言文件说明不了主路径可用。

## 缺陷修复的三步节奏

先构造能稳定触发的复现步骤，确认失败现象与报错一致；再动手改代码；最后用同一组步骤重跑，确认现象消失。跳过复现就无法排除「问题根本不在这里」，跳过重跑则分不清是真修好了还是触发条件变了。能固化成修复前失败、修复后通过的回归用例最好。

## 完成声明不等于产物可用

背景任务返回成功只说明进程正常退出，不代表文件真被改对。汇总阶段按验收条件逐项核对：改动是否落在约定文件里、接口签名是否与契约一致、有没有留下占位或未迁移的调用点。全量格式化与测试在并发改动收敛后集中跑一次。

## 测试只在能拦住回归时才写

新增用例的门槛是它能被一个合理的缺陷弄失败：契约边界、状态迁移、优先级顺序、真实错误分支值得写。只断言字段转发或日志文案的用例只会在重构时制造噪声，遇到这类既有用例应当删除而不是改文案重新钉住。
