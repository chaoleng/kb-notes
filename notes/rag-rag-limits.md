# RAG（检索增强生成）：RAG 的边界与适用场景

> RAG 适合知识查找和基于资料的问答，但不能替代所有数据库查询、计算和业务操作。

## 检索答不了的四类问题
一是精确聚合，「上季度华东退款总额」靠 top-k 片段只能拿到样本，求和必然漏数；二是事务性操作，下单、改密码、发起退款需要幂等与审计，不是生成文本；三是强时序计算，同比、环比、滚动七日均值依赖完整序列；四是全库扫描型分析，例如「还有多少文档在引用旧接口」，本质是遍历而非相似度排序。

## 该走的路径
前三类交给 SQL 或业务 API，由模型负责生成查询语句、选择函数参数，拿到确定结果后再回填成自然语言；第四类交给批处理作业，把扫描结果物化成一张结果表，之后再让检索去读这张表。

## 路由怎么判断
在问题理解阶段加一层分类器：出现总数、平均、排名、环比等聚合词，或带明确时间区间、指向单一主键的实体时，路由到工具链；开放式的「怎么做」「为什么」「有哪些注意事项」才走检索。两类错误代价不对称，宁可先试工具再回退到检索。

## 混合形态最常见
线上多数问题是先用 SQL 取准确数字，再用检索找解释口径的文档，两段证据一起进上下文。
