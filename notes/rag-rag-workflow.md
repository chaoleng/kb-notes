# RAG（检索增强生成）：RAG 端到端工作流

> 理解问题、找证据、组织上下文、生成答案和评估反馈的完整闭环。

## 一次查询的实际时序
问题进来先补全指代并拆成 2–3 个子查询，然后向量检索与 BM25 并行各取 top50，用 RRF（k=60）融合到 top30，cross-encoder 重排后留前 8 段，按预算截断拼入模板，生成结束再逐句核对引用编号是否落在证据集合内。

## 每一步的延迟量级
小模型改写约 200–400ms，双路召回并行只要 20–60ms，重排 8 段在 GPU 上 30–80ms、纯 CPU 可能升到 300ms，生成首 token 300–800ms、完整答案 2–5 秒。瓶颈几乎都在两次模型调用上，检索通常占不到总耗时的一成。

## 中间产物必须留痕
改写后的子查询、各路召回的 doc id 与原始分数、融合名次、重排分数、最终进入上下文的 chunk id，全部按 trace id 落日志。复盘答错案例时先看证据里究竟有没有正确答案，再区分是召回问题还是生成问题。

## 降级路径
重排超时就直接用融合结果，改写超时就退回原始问题，证据全空则返回明确的「资料不足」而不是让模型硬编。
