# 重排序器（Reranker）：Top-K、延迟与上下文预算

> 候选数量、重排数量和最终保留数量共同决定质量、延迟和模型上下文成本。

## 三级收缩 K1 → K2 → K3
先用低成本通道召回 K1 条组成较大的候选集，再让重排模型对其中 K2 条打分，最后只保留 K3 条拼进提示词。三个数字单调递减，受不同资源约束：K1 受索引参数（如 HNSW 的 efSearch）与扫描成本限制，K2 受模型算力限制，K3 受上下文窗口和生成质量限制。

## 各级的典型量级
常见配置是 K1 取 100–200（混合检索时每路各取 50–100 再融合），K2 取 50，K3 取 3–5。K3 很难再放大：512 token 的片段取五条已是 2.5k token，叠加系统指令与对话历史就逼近预算上限，而且无关内容越多，模型越容易被带偏。

## 延迟和 token 账怎么摊
把 p95 拆开看：向量查找与 BM25 各占十几到几十毫秒，重排五十条约几十毫秒，生成通常占大头。重排是唯一随 K2 线性膨胀的一段，K2 从 50 提到 200 会让检索侧耗时翻几倍；K3 每加一条片段，既抬高 prefill 成本，也拖慢首 token 返回。

## 截断位置靠离线评估定
重排提升相关性的同时必然增加延迟和调用成本，所以候选数量与截断位置都要用离线评估定下来：扫 K1/K2/K3 的网格，找 Recall@K1 饱和的拐点（再加候选也捞不到新证据就停手），再看重排后进入前 K3 的增量是否值回这段延迟。线上再用分位数耗时和答案质量复核一遍。
