# 文档切分（Chunking）：父子片段检索

> 用小片段负责精准召回，再取其父章节或邻近片段补充完整上下文。

## 索引里放什么
只给子片段建向量，典型长度 128–256 token；父片段是 1000–2000 token 的整节，存在 KV 或文档库里，不进向量索引——长文本编码后会被平均成一个模糊向量，反而拉低区分度。子片段的 metadata 至少携带 `parent_id`、`doc_id`、`chunk_index` 以及在原文中的起止 offset。

## 召回到补全的流程
向量检索取 Top-20 子片段，按 `parent_id` 聚合，同一父节被多次命中时只回表取一次文本，排序分取其子片段的最高分。父节仍然过长时改用窗口扩展：只拼接命中片段前后各一个兄弟片段，而不是整节塞进去。

## 上下文预算冲突
父级补全会把送进模型的 token 放大三到五倍。8K 窗口下，5 条 1500 token 的父节就已经溢出，所以顺序必须是先重排后补全：交叉编码器在子片段粒度上排序，只对前 3 条做父级扩展，其余保留子片段原文。

## 容易踩的坑
引用定位要落在子片段的 offset 上，否则用户点开只看到一整节，找不到答案在哪一句。父文档更新时要级联重算它名下全部子片段的向量，只改父文本会让检索继续命中已经过期的子片段。
