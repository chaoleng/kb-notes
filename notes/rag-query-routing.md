# RAG：查询路由与意图分类

> 先判断该不该检索，再判断该检索哪个子库，路由的两级决策决定了后续链路的上限。

## 第一级：要不要检索
入口先分三支：闲聊寒暄直接由模型回答；要精确数字或写操作的走 SQL 与业务 API（理由见 [RAG 的边界](note://rag-rag-limits)）；剩下的开放式知识问答才进检索。判错的症状很好认——闲聊被塞进五段无关文档后，模型开始一本正经地引用它们。

## 第二级：路由到哪个库
生产知识库通常不是单一索引，而是按产品线、文档类型（API 文档／运维手册／工单）、语言和租户切成多个命名空间。路由输出的是命名空间列表加结构化过滤条件。分不清就多选：命中两个库各取 top-20，成本只翻一倍，远好过押错单库。

## 三种分类器的延迟与准确率
规则匹配延迟不到 1 毫秒、可解释，但规则表随业务膨胀，覆盖率常卡在七成；微调的 BERT-base 量级分类器延迟 5–20 毫秒、准确率可过 95%，代价是几千条标注与新类目重训；LLM 判定零标注、能接长尾意图，但多花 300–800 毫秒，且类目会漂移，必须用受限解码钉在枚举值上。

## 代价不对称
该检索却没检，用户拿到的是幻觉，错误不可见；不该检却检了，只多花几十毫秒和一次向量查询，重排还能压掉噪声。所以阈值要偏向多检：走检索的置信度低于 0.8 才判为不检索。这一层的其余动作见[用户问题理解](note://rag-question-understanding)。
