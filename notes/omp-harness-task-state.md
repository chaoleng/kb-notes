# omp Harness：待办与阶段状态管理

> 用 todo 把多步任务外化成可检查的阶段状态，靠真实任务文本、显式阻塞标记和与工具调用同轮的状态更新保持进度可信。

## 为什么要外化进度

多步任务的进度只存在模型记忆里时会随窗口推进而失真：做过的步骤被重做，没做的被当成已完成。`todo` 把每一步写成一条可检查的条目，状态在 `pending`、`in_progress`、`completed`、`blocked` 之间显式迁移，随时能对照清单判断还剩什么。

## 任务文本要有实质

条目文本是给人看的检查项，必须写清做什么，例如「把索引重建脚本切到新 schema 并跑一次空库导入」；退化成「步骤一」「步骤二」这类自动编号后，清单就只剩计数功能，失去了核对价值。粒度以一条对应一次可验证的产出为宜，太粗无法判断进展，太细则维护清单的开销超过收益。

## 阻塞要标出来而不是跳过

遇到依赖缺失、外部服务不可用、需要用户决策的情况，把条目置为 `blocked` 并写明卡在哪里，继续推进其他可做项。静默跳过的危害是：清单显示一切正常，实际交付缺了一块，问题在最终验收时才暴露，返工成本最高。

## 状态与动作同轮发出

标记 `in_progress` 要和真正动手的那次工具调用在同一轮，标记 `completed` 要在改动已经落地之后。提前勾完或事后补记，都会让清单与仓库真实状态脱节。清单属于过程记忆，用于自我追踪而非对外结论，分层见 [记忆管理](note://omp-harness-memory-management)。
